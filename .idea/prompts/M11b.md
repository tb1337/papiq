## Ziel
Regeln sind vollständig über die Oberfläche pflegbar: Liste, Baukasten für Bedingungen und
Aktionen, Versionen, Aktivieren und Deaktivieren, Probelauf und rückwirkendes Anwenden mit
Auswahldialog. Admins haben in API und UI die Rechte, die Entscheidung 1 festlegt. Alles in
Design B, zweisprachig, per Tastatur bedienbar. Die CI bleibt schnell.

## Umfang

### Querschnitt
- Grundlage ist das Gerüst aus M10 und M11a (siehe „Übergaben an M11b“): Seiten unter
  `src/routes/(app)/…`, Platzhalter `/ui/rules` ersetzen, Bausteine aus shadcn-svelte per CLI,
  Importe `#lib/…`, API nur über `api` aus `#lib/api/client.ts`, Fehler über
  `describeError`/`reportError`, 422-Details über `fieldErrors`, Stammdaten über `loadLookup`.
- Jeder sichtbare Text in `messages/{en,de}.json`. Fehlertexte der API bleiben, wie sie kommen.
- Lade-, Leer- und Fehlerzustände; ändernde Aktionen mit Toast, zerstörende mit
  Bestätigungsdialog.
- Rechte: Die UI zeigt Aktionen nur, wenn sie erlaubt sind; die API bleibt die einzige Prüfung.
- Seitenpfade nur mit IDs. Barrierefreiheit wie M10/M11a (Tastatur, Fokus, WCAG AA).

### Phase A – Admin-Rechte (Entscheidung 1)
Befund aus M11a, im Code nachgeprüft:
- **Webhooks:** Der Kern erlaubt Admins Test und Geheimnis erneuern bereits
  (`manageable_webhook`, `send_test`); nur die Endpunktbeschreibungen von
  `POST /webhooks/{id}/test` und `POST /webhooks/{id}/secret` sagen „Owner only“, und die UI blendet
  beides für fremde Webhooks aus (`webhooks/+page.svelte`). Beschreibungen korrigieren, UI
  nachziehen, Test für Admin auf fremdem Webhook ergänzen, falls er fehlt.
- **Verarbeitungsprotokoll:** `GET /documents/{id}/log` ist im Kern „Owner only“
  (`permissions.py`, `documents.py`). Für Admins öffnen nach Entscheidung 1.
- **Schubladen:** `GET /drawers` liefert Admins nur eigene und freigegebene
  (`DrawerService.list` → `drawers.list_accessible`). Für Admins alle liefern; das braucht eine
  Abfrage aller Schubladen im Port `DrawerRepository` mit Vertragstest (freigegeben durch
  Entscheidung 1).
- Weitere Punkte je nach Entscheidung 1 (Dokumente, Schubladen verwalten, Nutzer-Regeln).
- Docstring in `permissions.py`, Abschnitt „Berechtigungen“ und „Sichtbarkeit“ der Regel-Engine in
  `architektur.md` an die Entscheidung anpassen.
- Rechte-Tests: je geänderter Funktion Admin, Besitzer, Freigabe, fremder Nutzer, deaktivierter
  Admin.

### Phase B – Regelliste und Baukasten
- **Liste:** `GET /rules` in Ausführungsreihenfolge, getrennt oder markiert nach global und eigen,
  aktiv/inaktiv (auch „deaktiviert, weil eine Referenz gelöscht wurde“, sofern die API das
  liefert), Priorität, Auslöser. Admins schalten auf „alle Nutzer“ (`all_users=true`) um und sehen
  den Besitzer.
- **Baukasten:** Name, Priorität, Auslöser (Eingang, Änderung), Bedingungsbaum aus UND/ODER-Gruppen,
  jede Gruppe negierbar, beliebig verschachtelt; je Bedingung Feld, Operator, Wert. Operatoren und
  Werteingabe passen zu Feld und Attribut-Datentyp (wie `ConditionSchema` und die Prüfung im Kern;
  Werteingaben über `AttributeField` bzw. Auswahl aus Stammdaten). Aktionen: Schublade, Kontakt,
  Typ, Titel (mit Platzhaltern, Liste der Platzhalter sichtbar), Tags hinzufügen/entfernen,
  Attribut setzen, Prüfung erzwingen. Globale Regeln bieten nur Tags, Attribute und Prüfung
  erzwingen an; Schubladen nur, in die der Besitzer schreiben darf.
- Speichern mit `POST`/`PUT`; 422 und 404 erscheinen an der betroffenen Bedingung bzw. Aktion.
  Eine gespeicherte Regel erscheint im Baukasten unverändert (Rundlauf JSON → Baukasten → JSON,
  mit Tests).
- **Aktivieren/Deaktivieren** (`PATCH`), **Löschen** mit Bestätigung, **Versionen** (`/versions`):
  Liste und Anzeige einer Version (Entscheidung 4).

### Phase C – Probelauf und rückwirkendes Anwenden
- „Auf bestehende Dokumente anwenden“ an der Regel: `POST /rules/{id}/apply/preview` seitenweise
  (Cursor), je Dokument die Änderungen (alt → neu), Konflikte markiert, Hinweise. Auswahl nach
  Entscheidung 3; Konflikte nur mit ausdrücklichem Haken (`accept_conflicts`).
- `POST /rules/{id}/apply` mit Version und Auswahl; Fortschritt über
  `GET /rule-applications/{id}` (es gibt keine Ereignisse dafür, siehe M8), Ergebnis mit
  übersprungenen Dokumenten und Grund.
- Probelauf vor dem Speichern einer neuen oder geänderten Regel: Entscheidung 2.
- Vorlage für die Darstellung der Folgen: der Probelauf-Dialog des `DocumentEditor`.
