# Aufgabe: Meilenstein M3 – Ingest-Pipeline

Empfohlener Start: `claude --model opus --effort high`

Voraussetzung: M2 (`m2-persistence`) ist in `main` gemergt.

## Kontext
Lies zuerst vollständig:
- `CLAUDE.md`, `backend/README.md`
- `.idea/architektur.md` (verbindlich), besonders: Datenhaltung, Ingest-Workflow, Asynchronität und
  Ereignisse, Betrieb, Schnittstellen
- `.idea/umsetzungsplan.md`, Abschnitt M3 **inklusive „Übernommen aus M2"**
- `backend/src/papiq/core/` – vor allem `domain/pipeline.py`, `services/pipeline.py`, `services/documents.py`

- `backend/src/papiq/adapters/outbound/` (memory, sql) und `backend/src/papiq/composition/`

Halte Dich an die getroffenen Entscheidungen. Fehlt eine Entscheidung oder ist etwas unklar, frag
mich, bevor Du es umsetzt. Ports und Vertragstests aus M1/M2 ändern nur nach Rücksprache.

## Ziel
Ein Dokument (PDF oder Foto) wird per API eingeliefert, sofort mit `202 Accepted` quittiert und vom
Worker im Hintergrund durch Empfangen → OCR → Parsen verarbeitet. Fortschritt per Server-Sent Events,
jeder Schritt einzeln wiederholbar. Klassifizieren, Attribute und Regeln bleiben Platzhalter (M5/M7).

## Arbeitsweise
1. Plan-Modus zuerst. Lege mir vor: Ablauf je Schritt, Port-Signaturen für OCR und Parser,
   Prozessmodell für rechenlastige Schritte, API-Endpunkte, Worker-Lebenszyklus, Lösungen für die
   Punkte aus „Übernommen aus M2", neue Konfigurationsvariablen, Teststrategie, Annahmen und offene
   Fragen. Beginne erst nach meiner Freigabe.
2. Branch `m3-ingest`. Arbeite in drei Phasen und melde Dich nach jeder Phase mit einer kurzen
   Zusammenfassung, bevor Du weitermachst:
   - **Phase A:** Objektspeicher-Adapter (Dateisystem, S3/Garage) mit Vertragstests.
   - **Phase B:** OCR- und Parser-Adapter, Pipeline-Schritte, Worker-Dienst.
   - **Phase C:** REST-API mit Upload, Status, Wiederholen, SSE.
3. Kleine thematische Commits, alle fünf Checks vor jedem Commit.
4. Zum Schluss: separater Agent prüft gegen Architektur, Ports und „Fertig, wenn"; Befunde beheben;
   Pull Request gegen `main`.

## Umfang

### Phase A – Objektspeicher
- Adapter `filesystem` (atomares Schreiben: temporäre Datei, dann umbenennen) und `s3` (Garage).
- Beide bestehen die Objektspeicher-Vertragstests aus M1 (S3 als Integrationstest im Devcontainer).
- Auswahl per `PAPIQ_STORAGE_TYPE` in der Composition Root.
- Prüfe, ob das bytes-basierte `put`/`get` des Ports für die erwarteten Dateigrößen reicht. Falls
  Streaming nötig ist: Vorschlag im Plan, Port-Änderung erst nach meiner Freigabe.

### Phase B – Verarbeitung
- **Ports `Ocr` und `DocumentParser`** mit echten Signaturen; In-Memory/Fake-Adapter und Vertragstests.
- **OCR-Adapter (OCRmyPDF):** Archiv-PDF (PDF/A) mit Textlayer; Seiten mit vorhandenem Text nicht neu
  erkennen; Sprachen per `PAPIQ_OCR_LANGUAGES` (Default `deu+eng`). Fotos (JPEG, PNG, TIFF) werden
  dabei zu PDF.
- **Parser-Adapter (Docling):** Markdown und JSON aus dem Archiv-PDF. Docling-Modelle dürfen zur
  Laufzeit nicht aus dem Internet geladen werden: im Plan festlegen, wie sie in Devcontainer und
  (später, M9) Image vorab bereitstehen.
- **Rechenlastige Schritte** laufen in eigenen Prozessen, damit die Event-Loop frei bleibt;
  Zeitlimit pro Schritt.
- **Derivate** im Objektspeicher: Archiv-PDF, Docling-Ausgabe; Vorschaubild der ersten Seite
  vorschlagen (neue Abhängigkeit nur nach Abstimmung).
- **Nicht unterstützte Dateitypen:** Vorschlag im Plan (z. B. sofort Rot mit klarem Grund).
- **Retries:** Anzahl und Abstand automatischer Wiederholungen per Konfiguration; Vorschlag für Defaults
  im Plan (offener Punkt der Architektur).
- **Worker-Dienst** (eingehender Adapter `worker`): Jobs claimen und ausführen, parallele Jobs per
  Konfiguration, Outbox-Verteilung per Polling (`EventBus.dispatch`), Aufräum-Job für erledigte Jobs
  und vollständig zugestellte Outbox-Einträge, sauberes Herunterfahren bei SIGTERM (laufende Jobs
  beenden oder Lease verfallen lassen), Datenbank-Engine schließen.
- **SQLite-Regel aus M2:** Ein Task öffnet keine zweite schreibende Unit of Work, solange seine erste
  offen ist. Im Plan zeigen, wie Worker und API das einhalten.
- Obergrenze oder wachsender Abstand für fehlgeschlagene Ereigniszustellungen.

### Phase C – REST-API (eingehender Adapter `rest`, FastAPI)
- `POST /documents`: Upload (Multipart), Größenlimit per Konfiguration, Datei wird beim Empfang
  gehasht, nicht vollständig im Speicher gehalten; Antwort `202 Accepted` mit Dokument-ID.
  Dublette desselben Besitzers → `409`.
- Status eines Dokuments, Verarbeitungsprotokoll, „Schritt wiederholen", „ab Schritt X neu verarbeiten".
- Server-Sent Events für Fortschritt; jeder Nutzer erhält nur Ereignisse zu Dokumenten, die er
  sehen darf.
- Health-Endpunkt.
- OpenAPI sauber: Schemas, Fehlerantworten, Beispiele.
- **Authentifizierung kommt erst in M4.** Schlage im Plan vor, wie API-Aufrufe in M3 einem Nutzer
  zugeordnet werden, ohne eine Hintertür zu schaffen, die nach M4 bestehen bleibt (z. B. eine
  austauschbare Abhängigkeit „aktueller Nutzer", die in Tests gesetzt wird). Keine Lösung, die im
  Betrieb unbemerkt aktiv sein kann.

### Start
API und Worker per Composition Root startbar (z. B. `python -m papiq.composition api` und `worker`),
unter Beachtung von `PAPIQ_ROLE`. s6-overlay folgt in M9.

## Neue Abhängigkeiten
Erlaubt: `fastapi`, `uvicorn`, `python-multipart`, `ocrmypdf`, `docling`. Für S3 und SSE schlägst Du
im Plan Bibliotheken vor; alles Weitere vorher abstimmen. Docling zieht PyTorch: nur die CPU-Variante.

## Testdaten
Kleine, im Test erzeugte oder eingecheckte Beispieldateien: ein PDF ohne Textlayer (Scan), ein PDF
mit Text, ein Foto, eine beschädigte Datei, ein nicht unterstützter Typ. Langsame Tests mit Docling
bekommen einen eigenen Marker, damit sie gezielt laufen können.

## Nicht Teil von M3
Authentifizierung und Nutzerverwaltung über die API (M4), Klassifizierung und LLM (M5), Suche (M6),
Regeln (M7), Webhooks und MCP (M8), Image und s6-overlay (M9), Office-Dateien und E-Mails.

## Fertig, wenn
- Ein gescanntes PDF und ein Foto laufen per API durch; Archiv-PDF und Docling-Ausgabe liegen im
  Objektspeicher (Dateisystem und Garage).
- Ein absichtlich abgebrochener Schritt lässt sich einzeln wiederholen; „ab Schritt X neu verarbeiten"
  funktioniert.
- Fortschritt kommt per SSE an, nur für berechtigte Nutzer.
- Eine Dublette desselben Besitzers wird abgelehnt.
- Worker fährt sauber herunter; Aufräum-Job entfernt alte Jobs und zugestellte Outbox-Einträge.
- Alle Checks, CI-Matrix und Devcontainer-Job grün.
