## Ziel
Papiq ist über die Oberfläche vollständig nutzbar, außer dem Pflegen von Regeln (M11b): Dokumente
hochladen, ansehen, bearbeiten und verschieben, Posteingang abarbeiten, suchen, Schubladen teilen,
Stammdaten und Nutzer verwalten (Admin), Webhooks, API-Tokens und die eigenen Einstellungen
pflegen. Alles in Design B, zweisprachig, per Tastatur bedienbar. Die CI bleibt schnell.

   - **Phase B – Posteingang und Suche.**
   - **Phase C – Schubladen und Freigaben, Stammdaten und Nutzer (Admin).**

## Umfang

### Querschnitt (alle Phasen)
- Grundlage ist das Gerüst aus M10 (siehe „Übernommen aus M10“ im Umsetzungsplan): Seiten unter
  `src/routes/(app)/…`, Platzhalter ersetzen, Bausteine aus shadcn-svelte per CLI, Importe `#lib/…`,
  API nur über `api` aus `#lib/api/client.ts`, Fehler über `describeError`/`reportError`, Formate
  über `#lib/i18n.ts`, Lanes über `LaneBadge`.
- Jeder sichtbare Text in `messages/{en,de}.json`. Fehlertexte der API bleiben, wie sie kommen.
- Lade-, Leer- und Fehlerzustände auf jeder Seite; ändernde Aktionen mit Rückmeldung (Toast),
  zerstörende mit Bestätigungsdialog.
- Rechte: Die UI zeigt Aktionen nur, wenn sie erlaubt sind (Rolle, Besitzer, Freigabe „lesen“
  oder „lesen/schreiben“), die API bleibt die einzige Prüfung. Admins haben alle Rechte und sehen
  alles, was die API ihnen liefert.
- Seitenpfade nur mit IDs, keine Namen als Pfadparameter (Punkt im letzten Abschnitt → 404).
- Barrierefreiheit wie M10: Tastatur, sichtbarer Fokus, WCAG AA, Lanes nie nur über Farbe.

### Phase A – Dokumente
- **Liste:** `GET /documents` mit Filtern (Kontakt, Typ, Tag, Schublade, Lane), Cursor mit
  „Mehr laden“ (Entscheidung 5), Vorschaubild (`/preview`), Titel, Kontakt, Typ, Datum, Lane.
  Filter stehen in der URL (teilbar, Zurück-Taste).
- **Detail:** Anzeige mit PDF.js (Archiv-PDF, sonst Original), Herunterladen von Original und
  Archiv, Metadaten (Titel, Datum, Kontakt, Typ, Tags, Attribute je Typ mit Eingabe passend zum
  Datentyp, Schublade). PDF.js lokal ausgeliefert, kein CDN, Worker als eigene Datei
  (`worker-src`).
- **Bearbeiten mit Probelauf:** Vor dem Speichern `POST /documents/{id}/dry-run`; die UI zeigt die
  Folgen (z. B. „wandert in Schublade Z – sichtbar für B“, Regeln, die greifen) und speichert erst
  nach Bestätigung (`PATCH`).
- **Verschieben** (`/move`), **Löschen**, **Protokoll** je Schritt (`/log`: Ergebnis, Konfidenz,
  Grund, Modell, Dauer), **Schritt wiederholen** (`/retry`) und **ab Schritt X neu verarbeiten**
  (`/reprocess`).
- **Upload:** Ziehen und Ablegen oder Dateiauswahl, mehrere Dateien (je Datei ein Aufruf, die API
  nimmt eine Datei pro Upload), Wahl der Schublade, Kanal `web`. Fehler je Datei (Dublette,
  zu groß, Format). Fortschritt danach per SSE bis zur Lane.
- **SSE:** ein `EventSource` auf `/api/v1/events` für die angemeldete Sitzung; Ereignisse sind
  schlank, die UI lädt den betroffenen Stand nach. Kein Replay: nach dem Wiederverbinden sichtbare
  Daten neu laden. Strom endet beim Abmelden und bei 401.

### Phase B – Posteingang und Suche
- **Posteingang:** `GET /inbox`, gruppiert bzw. filterbar nach Lane (Prüfen, Eingreifen) mit
  Grund. Prüfansicht (`/review`): Vorschläge des Modells mit Konfidenz und Grund je Feld, PDF
  daneben, Korrigieren und Bestätigen (`/confirm`); Rot mit Fehler und „Wiederholen“. Zähler in
  der Navigation, aktualisiert per SSE.
- **Suche:** `GET /documents/search` mit denselben Filtern wie die Liste, Treffer mit Ausschnitt (`snippet`),
  Suchbegriff in der URL, „Mehr laden“ über `next_offset`. Gewichtung Wörter/Bedeutung: Entscheidung 6.

### Phase C – Schubladen, Stammdaten, Nutzer
- **Schubladen:** eigene und geteilte anzeigen, anlegen, umbenennen, löschen (Standardschublade
  nicht), Freigaben je Nutzer mit „lesen“ oder „lesen/schreiben“ setzen und entziehen.
- **Stammdaten (Admin):** Kontakte, Dokumenttypen, Tags, Attribute (Datentyp, Geltungsbereich
  global oder je Typ, Optionen bei „Auswahl“, Währung bei „Betrag“) anlegen, ändern, löschen.
  Nutzer ohne Admin-Rolle sehen den Bereich nicht.
- **Nutzer (Admin):** Liste, anlegen (Rolle, Startpasswort), Rolle ändern, deaktivieren,
  Passwort zurücksetzen (mit „Tokens widerrufen“), TOTP und OIDC-Verknüpfung entfernen. Der
  Schutz des letzten aktiven Admins (409) erscheint als verständliche Meldung.

### Phase D – Webhooks, Einstellungen, API-Tokens
- **Webhooks:** Liste, anlegen und ändern (Ziel-URL, Ereignistypen), Geheimnis einmal anzeigen,
  Geheimnis erneuern, Test senden, Zustellprotokoll (`/deliveries`). Admins sehen fremde Webhooks
  wie die API sie liefert.
- **Einstellungen:** Passwort ändern; TOTP einrichten (QR-Code und Geheimnis als Text,
  Entscheidung 3; Bestätigen mit Code), Wiederherstellungscodes neu erzeugen, TOTP abschalten;
  OIDC verknüpfen und lösen (nur wenn eingerichtet); alle anderen Sitzungen beenden; Sprache und
  Darstellung (hell, dunkel, System).
- **API-Tokens:** Liste, anlegen (Name, Stufe lesen bzw. lesen + schreiben, optional Ablaufdatum), Token
  einmal anzeigen mit Kopieren, widerrufen.
- **Regeln:** Der Bereich bleibt ein Platzhalter mit Hinweis auf M11b (Entscheidung 1).

## Entscheidungen
<!-- Werden nach Tobis Antwort eingetragen. -->
1. **Aufteilung M11a/M11b:** Der ganze Bereich Regeln (Liste, Baukasten, Versionen, Probelauf
   einer Regel, rückwirkendes Anwenden) ist M11b. M11a lässt den Platzhalter stehen. Der
   Probelauf einer Dokumentänderung (`/documents/{id}/dry-run`) gehört zu M11a.
2. **Formulare:** weiter ohne Superforms, Zod und TanStack; Formulare mit den shadcn-Bausteinen und
   kleinen eigenen Helfern in `#lib`, Prüfung durch die API (422 an den Feldern anzeigen).
3. **QR-Code für TOTP:** eine kleine Bibliothek ohne Abhängigkeiten erzeugt den QR-Code im Browser
   als SVG (Paket und Version im Plan); das Geheimnis steht zusätzlich als Text daneben.
4. **OIDC-Fehler:** kleine API-Änderung in M11a: `/auth/oidc/callback` leitet bei einem Fehler auf
   `/ui/login?error=<Code>` um, die Anmeldeseite zeigt eine Meldung. Test im Backend, OpenAPI und
   Client neu erzeugen.
5. **Dokumentliste:** Reihenfolge der API (neueste zuerst), keine Sortierung durch den Nutzer,
   „Mehr laden“ statt Seitenzahlen. Keine API-Änderung.
6. **Suche:** keine Gewichtung in der UI; die API nutzt ihren Standard. Die offene Schwelle aus M6
   bleibt offen.
7. **Design:** keine neue Abstimmungsrunde per Artifact; die Bildschirme folgen Richtung B. Ich
   sehe sie über die Screenshots nach jeder Phase.
